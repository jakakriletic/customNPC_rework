# Scenarij M2.1 — instrumentacija in posnetek meritve

**Namen:** imeti številke, preden karkoli optimiziramo. Brez tega je vsaka trditev o
performancu mnenje.

**Vhodni pogoj:** M0.6 (skriptiran testni svet).
**Kdo to potrebuje:** M2.4–M2.6 (merilni scenariji in baseline), M5 (performance AI),
M3/M4 (dokaz, da popravek ni podražil ticka).

---

### Zakaj obstajajo števci `world.*` in `npc.tick.gap`

Prva meritev (15. 9.) je pokazala `npc.per.tick` p50 = 0 pri osmih NPC-jih v svetu — NPC-ji
so tikali le v približno vsakem petem ticku. Iz samega števca posodobitev se ne da ločiti med
"entitet v svetu ni", "entitete so, a so mrtve" in "entitete so žive, a jih nekaj ne tika".
Zato:

| Kar vidiš | Kaj to pomeni |
|---|---|
| `world.npc.loaded` niha | chunki z NPC-ji se nalagajo in odlagajo |
| `world.npc.loaded` = 8 konstantno, `npc.per.tick` p50 = 0 | NPC-ji so v svetu, a jih nekaj ne posodablja — iskati v vanilla `updateEntities` |
| `world.npc.killed` > 0 | NPC-ji so mrtvi in čakajo na respawn; meritev ne meri živih NPC-jev |
| `npc.tick.gap` enakomeren (npr. vedno 5) | sistematično; nekaj posodablja redkeje |
| `npc.tick.gap` razmetan | naključno; bolj verjetno chunk loading |

Rezervirana, a **še ne polnjena** imena: `ai.path.request`, `ai.path.failed`, `script.run`,
`script.lock.wait`, `ai.task.<RazredTaska>`. Klicna mesta zanje nastanejo, ko sta
`EntityNPCInterface` in paket `ai` prenesena (M3.1) oziroma ko je prenesen
`ScriptContainer` (M5.1/M6.6). Do takrat se v izpisu ne pokažejo, ker imajo števec 0.

### Zakaj je `npc.update.window` približek

`EntityNPCInterface` v tej fazi še ni v `src/patch/java`, zato vanj ni mogoče vstaviti
merilnika. Forge da le dogodek ob **začetku** posodobitve entitete. Svetovi posodabljajo
entitete zaporedno na server niti, zato se čas NPC-ja meri kot razmik med začetkom njegove
posodobitve in začetkom posodobitve naslednje žive entitete. V ta razmik je zajeta tudi
režija zanke, zato je vrednost **zgornja meja**, ne točna poraba. Točna meritev pride z
M3.1; takrat se ta stolpec primerja s tedanjim in razlika se zapiše.

## Kako se vklopi

Instrumentacija je privzeto **izklopljena** in takrat sploh ni prijavljena na Forge event
bus — v normalnem obratovanju ne stane niti enega klica na entiteto na tick.

```
/rwdiag on          # vklopi in počisti števce
/rwdiag status      # stanje, število tickov, trajanje
/rwdiag reset       # počisti števce, merjenje teče naprej
/rwdiag dump ime    # zapiše posnetek in ga izpiše v log
/rwdiag off         # izklopi in odjavi z event busa
```

Za scenarije, kjer je treba meriti že prvi tick, se server zažene z `-Drwdiag=on`.
Ukaz deluje tudi s konzole dedicated serverja (brez poševnice), zato ga skriptiran
scenarij lahko pošlje na standardni vhod, enako kot ukaze v `testworld-run.ps1`.

## Kam pride izpis

`dev/run/logs/rwdiag/rwdiag-<časovna-značka>-<ime>.txt` — berljiva tabela
`dev/run/logs/rwdiag/rwdiag-<časovna-značka>-<ime>.json` — isti podatki za primerjavo pred/po

Tabela gre tudi v CustomNPCs log in v konzolo. V konzoli so trije markerji, ki jih
verifikacijska skripta lahko poišče:

```
RWDIAG-DUMP <pot do datoteke>
RWDIAG-OK ticki=<n> npc=<n>
RWDIAG-NAPAKA <razlog>        (samo ob neuspehu)
```

## Kako se bere

```
stevec                            skupaj        na tick     ms/tick   povp. us
npc.update                        119483        199.138     -         -
npc.update.window                 119483        199.138     4.780     24.004

porazdelitev                      n         min       povp.     p50       p95       p99       max
server.tick.ns (ms)               600       20.058    32.690    33.030    44.040    44.957    44.957

  MSPT p95 = 44.040 ms od 50.000 ms proračuna (88.080 %)
```

- **`na tick`** je edina številka, ki je primerljiva med zagoni različnih dolžin.
- **MSPT p95** proti 50 ms je merilo, ali server še drži 20 TPS. Nad 50 ms strežnik zaostaja.
- Povprečje samo zase ne pove nič o zatikanju; vedno se gleda p95 in p99.
- Vrednosti v porazdelitvah so razvrščene v logaritemske koše s 32 podkoši na potenco
  dvojke, zato imajo do ~3,2 % napake navzgor. Števci (`skupaj`) so točni.

## Postopek

```powershell
.\dev.ps1 test --offline
.\dev.ps1 testOriginal --offline
.\dev.ps1 buildPatchedMod --offline
.\verify-package.ps1
.\testworld-run.ps1 -SkipSeed
```

Nato merila D4–D7 **skriptirano** (ročno tipkanje v gradle konzolo je 15. 9. dvakrat tiho
odpovedalo, zato je to edina merodajna pot):

```powershell
.\rwdiag-run.ps1                  # 60 s merjenja
.\rwdiag-run.ps1 -Seconds 180     # daljše merjenje
```

Skripta požene server, pošlje `rwdiag status` (mora biti `off`), `rwdiag on`, počaka, naredi
posnetek, izklopi, naredi še dva posnetka in primerja števce, nato ustavi server in izpiše
prvo tabelo. Izpis gre v `audit\m21-rwdiag.log`, posnetki v `dev\run\logs\rwdiag\`.
Izhodna koda 0 pomeni, da so D4–D7 zelena.

Posnetek se priloži v `docs/meritve/`, ko bo M2.6 postavil baseline.
