# Meritev — NBT↔JSON serializer (M1.1–M1.3)

Datum: 2026-09-11 · Paket: M1.1, M1.2, M1.3 · Zahteva: R9

## Kako je bilo merjeno

Vse spodaj je bilo izvedeno **proti pravi originalni kodi**, ne proti dekompilatu:

- `noppes.npcs.util.NBTJsonUtil` iz `dev/libs/customnpcs-mapped-01Oct19.jar`
- pravi 1.12.2 NBT razredi iz `forgeSrc-1.12.2-14.23.5.2847.jar`
  (Forge 14.23.5.2847, mappings `snapshot_20171003`)
- odvisnosti: guava 21.0, commons-io 2.5, log4j 2.8.1 — iste verzije kot v projektu

Meritve so tekle v oblačnem okolju te seje na OpenJDK 21, ne na Java 8 kot produkcijski build.
Absolutne številke se bodo na Javi 8 razlikovale; razmerja med starim in novim pa ne bistveno.
Ponovitev na Javi 8 je odprt opravek (glej spodaj).

## 1. Kaj je originalni serializer dejansko pokvaril

Vsak primer je bil pognan skozi `NBTJsonUtil.Convert(nbt)` → `NBTJsonUtil.Convert(json)` in
primerjan z vhodom.

| Primer | Vhod | Izhod po round-tripu | Ocena |
|---|---|---|---|
| long array | `[L;1L, 300L, 1234567890123L]` | `[L;1L, 44L, -53L]` | **vrednosti uničene** |
| prazen byte array | `[B;]` (tip 7) | `[]` (tip 9) | **spremenjen tip** |
| prazen int array | `[I;]` (tip 11) | `[]` (tip 9) | **spremenjen tip** |
| prazen long array | `[L;]` (tip 12) | `[]` (tip 9) | **spremenjen tip** |
| seznam intov | `[1, 2]` (tip 9) | `[I;1,2]` (tip 11) | **spremenjen tip** |
| seznam bytov | `[1b, 2b]` (tip 9) | `[B;1B,2B]` (tip 7) | **spremenjen tip** |
| seznam longov | `[1L, 2L]` (tip 9) | `[L;1L,2L]` (tip 12) | **spremenjen tip** |
| niz z vodilnim presledkom | `"  abc"` | `"abc"` | **izgubljeni znaki** |
| niz samo presledek | `" "` | `""` | **izgubljeni znaki** |
| niz z vodilnim `\n` | `"\nabc"` | `"abc"` | **izgubljeni znaki** |
| niz, ki se konča z `\` | `"path\"` | `StringIndexOutOfBoundsException` | **datoteka neberljiva** |
| `NaN` (double/float) | `NaNd` | `JsonException` | **datoteka neberljiva** |
| `Infinity` | `Infinityd` | `JsonException` | **datoteka neberljiva** |
| prazen ključ | `"": "x"` | zapisan brez ključa, nato `JsonException` | **datoteka neberljiva** |
| compound s 4000 ključi | — | `StackOverflowError` | **datoteka neberljiva** |

Kar je bilo **preverjeno in je delovalo pravilno že prej** (in mora tako ostati):
neprazni byte in int arrayi, seznami double/float/string/compound, prazni seznami in compoundi,
gnezdenje do globine 400, nizi z narekovaji, notranjimi `\`, prelomi vrstic, dvopičji,
zavitimi oklepaji in unicode znaki, vse skalarne vrednosti vključno z `Integer.MIN_VALUE`
in `Long.MIN_VALUE`, ter struktura tipa ItemStack z enchantmenti in lore.

### Popravek dveh napačnih trditev iz prvotne analize

Prvotni `docs/02-ZAHTEVE.md` je navajal dve hipotezi, ki sta se ob preverbi **izkazali za napačni**:

- **R9-d** — domneva, da se byte in long array zapišeta neparsljivo. Dejansko
  `NBTTagByteArray.toString()` v 1.12.2 vrne `[B;1B,2B]` in `NBTTagIntArray.toString()` vrne
  `[I;1,2]`; oba se pravilno preberata nazaj. Pokvarjen je samo long array, in sicer pri
  **branju** (`getByte()` namesto `getLong()`), ne pri pisanju.
- **R9-e** — domneva, da `SaveFile` ne zapre writerja. `javap -c` na originalnem bytecode
  pokaže, da se `OutputStreamWriter.close()` pokliče v obeh vejah (offset 36 in 49).
  Opozorilo dekompilerja *"Removed try catching itself"* je bilo artefakt CFR-ja.

To je natanko razlog, zakaj `docs/05-SEJA-PROTOKOL.md` zahteva preverbo z `javap`,
preden se karkoli popravi.

## 2. Diferencialni fuzz

4000 naključno generiranih NBT struktur (determinističen seed 0–3999; vsi NBT tipi,
homogeni seznami, gnezdenje do globine 4, nizi z narekovaji, `\`, oklepaji, dvopičji,
vejicami, prelomi vrstic in unicode znaki):

| | |
|---|---|
| Round-trip napak — **originalni** serializer | **1598 / 4000 (40 %)** |
| Round-trip napak — **novi** serializer | **0 / 4000** |
| Razlik v zapisanem besedilu (original proti novemu) | **0 / 4000** |

Zadnja vrstica je pomembna: **format datotek ostane nespremenjen**. Novi serializer zapiše
znak za znak isto besedilo kot original, zato:

- obstoječe clone/dialog/quest/player datoteke se berejo brez migracije,
- datoteke, ki jih zapišemo mi, zna prebrati nespremenjen CustomNPCs,
- za R9 **ni potrebna migracija save formata** (D-004 ostane v veljavi za kasnejše faze).

Edina namerna razlika v zapisu je prazen ključ: original ga zapiše brez `"": ` in s tem
naredi datoteko neberljivo; novi ga zapiše pravilno. Original tako datoteko zna prebrati.

## 3. Hitrost

Compound s 1500 ključi, 68.283 znakov izhoda (primerljivo z večjo clone ali dialog datoteko):

| Operacija | Original | Novi | Razmerje |
|---|---|---|---|
| zapis NBT → JSON | 235,3 ms | 2,9 ms | **81×** |
| branje JSON → NBT | 2386,3 ms | 6,5 ms | **367×** |

Vzrok je kvadratna gradnja nizov v obeh smereh (`json = json + tag + "\n"` pri pisanju,
`s = s + json.cut(1)` znak po znak pri branju) in rekurzija na ključ pri branju.

Kje se to pozna v igri: vse clone, dialog, quest, faction, recipe, transport, player in
script datoteke gredo skozi ta razred. Ob zagonu sveta se berejo vse naenkrat, `PlayerData`
pa se zapisuje ob vsaki spremembi. Ta postavka torej ni samo bugfix, ampak tudi merljiv
prispevek k **R5**.

## 4. Kaj to NE pokriva

- Meritev na Javi 8 (produkcijska verzija). Odprto.
- Datoteke, ki so **že** pokvarjene na disku. Izgubljenih long vrednosti in že prepisanih
  tipov ni mogoče rekonstruirati; to je naloga M1.4 (poročilo, ne ugibanje).
- Nevarni zapis datoteke v `ServerCloneController.saveClone` (izbriši → preimenuj brez
  preverbe rezultata). To je M1.5, ni del te meritve.
- Potrditev na uporabnikovi dejanski pokvarjeni datoteki. Še vedno odprto vprašanje Q3.
