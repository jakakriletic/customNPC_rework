# Server-side (TPS/MSPT) optimization of many AI entities in MC 1.12.2 Forge, applied to CustomNPCs

Scope note: web research plus reading of local, already-decompiled sources in this repository (no build or java process was run). Local sources are cited as `[local: <path>]`, relative to `C:\Users\jakak\Desktop\customNPC_rework`. `dev/build/tmp/recompileMc/sources/...` is the MCP-decompiled vanilla/Forge 1.12.2 code; `dev/reference-src/noppes/...` is decompiled original CustomNPCs 1.12.2.

Project constraints used for judging: (S) every change behind a switch with original as default; (F) lowering NPC tick frequency, sleeping distant NPCs and multithreaded AI are forbidden without a separate project; (P) packet IDs and NBT unchanged. "Behaviour-neutral" below means: same decisions, same paths, same packets, given the same world state.

## 1. Pathfinding: vanilla 1.12 cost centres and mods/patches that address them

### Takeaway
In 1.12 every path search builds a fresh `ChunkCache` over a cube of (followRange+8 or +16) blocks that calls `world.getChunkFromChunkCoords` (which can load chunks), then runs A* capped at 200 node expansions; the proven fixes for 1.12-era code are (a) do not load chunks while building the cache, (b) back off after repeated path failures, (c) do not recompute when the target has not moved, and (d) avoid redundant block-state lookups in the node processor. Only (d) and a correct form of (c) are strictly behaviour-neutral; (a) and (b) change edge-case behaviour and must be switches defaulting to off.

### Cited Findings
- Vanilla 1.12 `PathNavigate.getPathToPos` returns the cached path only if `currentPath` is unfinished and the target BlockPos is equal; otherwise it computes `i = (int)(followRange + 8)` and constructs `new ChunkCache(world, pos-i, pos+i, 0)` before `pathFinder.findPath(...)`. `getPathToEntityLiving` does the same with `i = (int)(followRange + 16)` around the entity's position+1. Both are wrapped in profiler section `"pathfind"`. — [local: dev/build/tmp/recompileMc/sources/net/minecraft/pathfinding/PathNavigate.java, lines 111-166]
- `getPathSearchRange()` is the entity's `FOLLOW_RANGE` attribute value. — [local: same file, lines 66-69]
- `PathNavigate.updatePath()` (block-change triggered repath) is already throttled to once per 20 world ticks; otherwise it sets `tryUpdatePath=true`. A stuck check runs every 100 ticks (`totalTicks - ticksAtLastPos > 100`). — [local: same file, lines 80-96, 316-323]
- `ChunkCache` constructor fills its array via `worldIn.getChunkFromChunkCoords(k, l)` for every chunk in the box (this goes through the chunk provider and can load/generate chunks), then scans those chunks for emptiness. — [local: dev/build/tmp/recompileMc/sources/net/minecraft/world/ChunkCache.java, lines 39-47]
- `PathFinder.findPath` stops after 200 iterations of the open set (`if (i >= 200) break`), uses a `HashSet closedSet` and a fixed `PathPoint[32]` options array. — [local: dev/build/tmp/recompileMc/sources/net/minecraft/pathfinding/PathFinder.java, lines 15-17, 56-94]
- CustomNPCs sets `FOLLOW_RANGE` base value to config `NpcNavRange` (default 32, min clamped to 16; config text: "Not recommended to increase if you have a slow pc or on a server"). — [local: dev/reference-src/noppes/npcs/CustomNpcs.java lines 122-123, 185-186; dev/reference-src/noppes/npcs/entity/EntityNPCInterface.java lines 334, 1049]
- CustomNPCs uses the vanilla navigators `PathNavigateGround`, `PathNavigateFlying`, `PathNavigateSwimmer` (so all vanilla PathNavigate/PathFinder/WalkNodeProcessor costs apply unchanged to NPCs). — [local: dev/reference-src/noppes/npcs/entity/EntityNPCInterface.java lines 762-768]
- Sponge (SpongeForge) has a config `disable-pathfinding-chunk-loads` ("Prevents pathfinding from loading chunks", default false). — [Sponge global.conf docs](https://docs.spongepowered.org/stable/en/server/getting-started/configuration/sponge-conf.html)
- Universal Tweaks (1.12.2) has "No Pathfinding Chunk Loading: Disables mob pathfinding from loading new/unloaded chunks when building chunk caches to improve performance". — [Universal Tweaks README](https://github.com/ACGaming/UniversalTweaks); [Universal Tweaks 1.11.0 on Modrinth](https://modrinth.com/mod/universal-tweaks/version/1.11.0)
- Paper/Spigot-era patch "Optimize Pathfinding" (Aikar, Jan 2016): adds `pathfindFailures` and `lastFailure` to `NavigationAbstract` (= MCP `PathNavigate`); `moveTo(entity, speed)` returns false without searching when `pathfindFailures > 10 && path == null && currentTick < lastFailure + 40`; counters reset on success and on `clearPath()`. Same patch replaces repeated `entity.world.getType()` calls in `PathfinderNormal` (= `WalkNodeProcessor`) with the already-held `IBlockAccess`/cached state, "reducing chunk lookups". Stated purpose: "Prevents pathfinding from spamming failures for things such as arrow attacks". — [FluxSpigot copy of 0087-Optimize-Pathfinding.patch](https://github.com/VictorML11/FluxSpigot/blob/master/Spigot-Server-Patches/0087-Optimize-Pathfinding.patch)
- MC-17630 "Zombie pathfinding to unreachable targets causes server lag": large numbers of zombies failing to find a path to unreachable villagers caused severe lag; fixed in 16w15b (1.9 cycle). — [Mojira MC-17630](https://bugs-legacy.mojang.com/browse/MC-17630)
- "Zombie Lag Fix" (Legacy Fabric, MC 1.6.4) backports "the pathfinding throttling code from 1.9.4"; "most of the reduction in CPU usage stems from not recalculating paths if the targeted entity (for example a villager) is not moving". No numbers published. — [Zombie Lag Fix on Modrinth](https://modrinth.com/mod/zombie-lag-fix)
- The only pathfinding work found in the AI Improvements issue tracker is an unreleased 1.7.10 "Pathfinder Tweaks" mod focused on correctness (fence hopping, slab hopping, pogo-sticking), with performance cost described as "negligible"; no speed-up measurements. — [BuiltBrokenModding/AI-Improvements issue #7](https://github.com/BuiltBrokenModding/AI-Improvements/issues/7)
- Modern (1.20+) "Path finder" mod: skips redundant path searches, throttles pathfinding bursts, and lowers AI tick rate of far mobs; hooks `PathNavigation.createPath`, `recomputePath`, `Brain.tick`, `Mob.serverAiStep`, `Level.setBlock`; uses MixinExtras `@WrapOperation`. — [Path finder on CurseForge](https://www.curseforge.com/minecraft/mc-mods/path-finder)
- Performant (1.14-1.16.5 only, no 1.12.2 build) claims "Multithreading of entity collisions and pathing". — [Performant on CurseForge](https://www.curseforge.com/minecraft/mc-mods/performant)
- VanillaFix's documented performance items are client/teleport/world-creation (animated textures, interdimensional teleport >10x faster); no pathfinding or ChunkCache optimization is documented. — [VanillaFix GitHub](https://github.com/DimensionalDevelopment/VanillaFix); [VanillaFix CurseForge](https://www.curseforge.com/minecraft/mc-mods/vanillafix)

### Inferences
- With default `NpcNavRange=32`, `getPathToEntityLiving` builds a ChunkCache with half-size 48 blocks (97-block cube), i.e. typically 6-7 chunks per horizontal axis, about 36-49 chunk lookups plus a section-emptiness scan per search, before A* even starts. With `getPathToPos` it is half-size 40 (about 25-36 chunks). For hundreds of NPCs that repath while chasing a moving target (target BlockPos changes, so the cached-path shortcut in `getPathToPos`/`getPathToEntityLiving` misses), this setup cost can rival the A* itself. This is a candidate for profiling, not a measured fact.
- Behaviour-neutral candidates (good fit for constraint S): (1) avoid redundant block-state lookups inside the NPC's node processor (the Paper `PathfinderNormal` part); (2) reuse a ChunkCache across searches only when it provably reflects the same world state (e.g. within one tick, same box) — but any block change in between breaks neutrality, so this needs care; (3) cheaper `closedSet`/node bookkeeping (data-structure only) as long as tie-breaking order in the binary heap is preserved, otherwise different (equal-cost) paths can be chosen.
- Behaviour-changing candidates (switch, default off): (a) no chunk loading in ChunkCache (NPCs at the edge of loaded area will treat unloaded chunks as impassable/air instead of loading them; also changes chunk-load side effects); (b) Paper failure back-off (NPC stops retrying for up to 40 ticks after >10 consecutive failures; visible as delayed reaction when the path becomes possible); (c) "don't recompute if target hasn't moved" — vanilla already returns the current path when the target BlockPos is unchanged and the path is unfinished, so further gains require skipping searches when the previous search failed for the same target (behaviour change).
- Because CustomNPCs owns its entity class, all of these can be applied by overriding `createNavigator`/a custom `PathNavigateGround` subclass for NPCs only, rather than global mixins into vanilla — which keeps vanilla mobs untouched and makes the switch trivially local.
- KAMKEEL issue #92 (see section 6) — 100 NPCs, aggro range 64, lag when the player moves fast/flies — is consistent with path searches being invalidated every time the target's BlockPos changes; this is a hypothesis, the issue has no profile.

### Gaps
- No published 1.12-specific measurement of ChunkCache construction cost vs. A* cost was found.
- No 1.12 Forge mod was found that replaces WalkNodeProcessor/PathFinder for speed (as opposed to correctness). Lithium-style pathfinding block-type caching ("ai.pathing" in Lithium) exists only for 1.15+ Fabric and was not researched in detail here.
- I could not find a primary source for the exact 1.9 `EntityAIAttackMelee` repath-delay formula; the vanilla 1.12 code in `dev/build/tmp/recompileMc/sources/net/minecraft/entity/ai/EntityAIAttackMelee.java` is the authoritative reference and was not read in this pass. Note CustomNPCs uses its own melee/ranged AI classes in `noppes.npcs.ai`.

## 2. AI task (goal selector) cost and backportable optimizations

### Takeaway
In 1.12 `EntityAITasks.onUpdateTasks` re-evaluates every non-running task's `shouldExecute()` (plus `canUse` mutex checks against all running tasks) every 3rd tick, checks `shouldContinueExecuting()` of running tasks on the other two ticks, and calls `updateTask()` of every running task every tick. The best-documented 1.12 gain is AI Improvements' EntityLookHelper replacement (claimed 50-80% less AI CPU, 5 to 7 TPS on a 25-player server); later-version goal-selector optimizations are mostly data-structure changes and caching that can be backported behaviour-neutrally if iteration order is preserved.

### Cited Findings
- 1.12 `EntityAITasks`: `taskEntries` and `executingTaskEntries` are `LinkedHashSet`s; `tickRate = 3`; `if (tickCount++ % tickRate == 0)` loop over all tasks: running ones are stopped if `!canUse || !shouldContinueExecuting`, idle ones started if `canUse && shouldExecute()`; else-branch only checks `shouldContinueExecuting` of executing tasks; afterwards `updateTask()` on all executing tasks every tick. Profiler sections `goalSetup` and `goalTick`. `canUse` iterates all executing tasks comparing priority, mutex bits and `isInterruptible()`. — [local: dev/build/tmp/recompileMc/sources/net/minecraft/entity/ai/EntityAITasks.java, lines 15-21, 64-173]; field list confirmed in [Forge 1.12.2 javadoc EntityAITasks](https://forge.yue.moe/javadoc/1.12.2/net/minecraft/entity/ai/EntityAITasks.html)
- The project already has a test noting the scheduler checks starts every 3rd call (`tickRate`). — [local: dev/src/test/java/noppes/npcs/rework/ai/AttackPriorityTest.java line 87]
- AI Improvements (1.12.2, config `config/bbm/AI_Improvements.cfg`): (1) "Disable Watch Closest Entity" (default false; "Visually this will cause a few odd issues"); (2) "Disable Look Idle" (default false; "can cause the entities head to not rotate sometimes but mostly goes unnoticed"); (3) EntityLookHelper replacement, enabled by default, caches calculated values at a minor RAM cost; claimed "50% to 80% decrease in CPU usage by the AI code" and, "for a server with 25 people on constantly", "a gain from 5 to 7 tps". The author notes much lower impact on newer versions due to built-in AI fixes. — [AI Improvements on CurseForge](https://www.curseforge.com/minecraft/mc-mods/ai-improvements); [Modrinth 1.12.2 build](https://modrinth.com/mod/ai-improvements/version/0.0.1b3)
- Universal Tweaks (1.12.2): "Watching AI Removal: Removes watching/looking entity AI for improved server performance"; "Watching AI Replacement: Replaces watching/looking entity AI for improved server performance"; "Concurrent Entity AI Tasks: Replaces linked entity AI task sets with concurrent sets to avoid mod exception concerning entity AI". — [Universal Tweaks README](https://github.com/ACGaming/UniversalTweaks)
- CustomNPCs registers its own `noppes.npcs.ai.EntityAIWatchClosest(this, EntityLivingBase.class, 5.0f)` instead of vanilla's, so vanilla-targeted mixins (AI Improvements' WatchClosest removal, UT's Watching AI replacement) may not apply to NPCs; the vanilla `EntityLookHelper` used by `getLookHelper()` would still be replaced by AI Improvements. — [local: dev/reference-src/noppes/npcs/entity/EntityNPCInterface.java lines 173, 899; dev/reference-src/noppes/npcs/ai/EntityAIWatchClosest.java]
- Performant (1.14-1.16.5): "Less AI overhead. AI's no longer spent like half their time deciding which task they should run" (no numbers published). — [Performant on CurseForge](https://www.curseforge.com/minecraft/mc-mods/performant)
- Paper has a patch "Optimize GoalSelector Goal.Flag Set operations" (1.14+ GoalSelector, flag-set handling in `setControlFlag`-type code). — [PaperMC commit ea1efef (patch list)](https://github.com/PaperMC/Paper/commit/ea1efef1164aa7653119eb4be000749930e5b4da); details of the patch body were not retrieved.
- Paper PR #11942 "Optimise tempt goal": originally each entity with TemptGoal checked items of every player in the world every tick ("100,000 checks" for 2,000 entities and 50 players); new code computes once per tick which players qualify and caches in a lazily computed BitSet. Measured: TemptGoal from 2.2% to 0.17% of tick time (50 bots, 500 pigs), "~1 mspt decrease"; later 0.74 mspt to 0.05 mspt. Behaviour parity except values cached within a tick. — [PaperMC PR #11942](https://github.com/PaperMC/Paper/pull/11942)
- "Goal Optimizer" mod: "Goal Selector optimization and configurable animals goals registry", archived, no mechanism/numbers on its page. — [Goal Optimizer on CurseForge](https://www.curseforge.com/minecraft/mc-mods/goal-optimizer)

### Inferences
- Behaviour-neutral backport candidates for the NPC's own `EntityAITasks` use: (1) precomputing mutex-compatibility so `canUse` does not loop all executing tasks (must give identical true/false); (2) replacing `LinkedHashSet` iteration with arrays while preserving insertion order (order matters: task start/stop order affects which mutex wins); (3) "compute once per tick, share across NPCs" caches in the style of Paper's TemptGoal patch — e.g. nearest-player/nearest-target scans used by WatchClosest/target-finding — strictly neutral only if the cached value would not change within the tick (any entity moving earlier in the same tick breaks exact parity; Paper accepted this as "doesn't meaningfully affect gameplay", which this project would have to treat as a behaviour change behind a switch).
- A look-helper with cached trig (AI Improvements style) is neutral only if it reproduces vanilla float results bit-for-bit; "fast trig" approximations change head angles slightly (visual) and possibly anything that reads rotation (e.g. ranged aim). Treat as switch default-off unless proven identical.
- Removing WatchClosest/LookIdle is a visible behaviour change (heads stop tracking players) — switch, default off.
- Changing `tickRate` from 3 or skipping `updateTask()` would fall under the forbidden "lower NPC tick frequency" category.

### Gaps
- No published 1.12-specific profile breakdown of goalSetup vs goalTick for modded NPCs was found.
- AI Improvements' source (BuiltBrokenModding) was not read; whether its LookHelper is bit-identical to vanilla is unverified.
- Paper's GoalSelector patch body and gains were not retrieved.

## 3. Entity collision / getEntitiesWithinAABB cost with many entities

### Takeaway
Each living entity in 1.12 performs at least two entity-AABB queries per tick (one in `Entity.move` via `getCollisionBoxes`, which scans entities in the AABB grown by 0.25 only to find the rare entities with solid collision boxes like boats, and one in `collideWithNearbyEntities` for pushing/cramming), and each query scans all chunk entity-lists overlapping the box expanded by `World.MAX_ENTITY_RADIUS` (vanilla 2.0, which mods may raise). In a dense NPC crowd this is O(n^2) per chunk section; proven mitigations are capping collisions (Spigot/Paper/Sponge, behaviour change), shrinking radius scans (Universal Tweaks), and Lithium's class-grouping (newer versions, behaviour-neutral in principle).

### Cited Findings
- `EntityLivingBase.collideWithNearbyEntities()` calls `world.getEntitiesInAABBexcluding(this, getEntityBoundingBox(), EntitySelectors.getTeamCollisionPredicate(this))`, then reads game rule `maxEntityCramming`; cramming damage applies when `list.size() > cramming-1` with a 1/4 random chance. — [local: dev/build/tmp/recompileMc/sources/net/minecraft/entity/EntityLivingBase.java lines 2670-2679]
- `World.getCollisionBoxes(Entity, AABB)` (used by movement) additionally calls `getEntitiesWithinAABBExcludingEntity(entityIn, aabb.grow(0.25D))` and iterates them to collect entity collision boxes. — [local: dev/build/tmp/recompileMc/sources/net/minecraft/world/World.java lines 1492-1502]
- `World.MAX_ENTITY_RADIUS = 2.0D` is a public static (mutable) field; entity-AABB queries compute the chunk range as `floor((minX - MAX_ENTITY_RADIUS)/16)` .. `floor((maxX + MAX_ENTITY_RADIUS)/16)`. — [local: dev/build/tmp/recompileMc/sources/net/minecraft/world/World.java lines 74, 3270-3273, 3329]
- Universal Tweaks: "Entity Radius Check: Reduces the search size of various AABB functions for specified entity types to improve performance". — [Universal Tweaks README](https://github.com/ACGaming/UniversalTweaks)
- CustomNPCs NPCs override `canBePushed()` as `super.canBePushed() && display.getHasHitbox()`. — [local: dev/reference-src/noppes/npcs/entity/EntityNPCInterface.java lines 1602-1603]
- Spigot `max-entity-collisions` (default 8): "Limit a single entity to colliding x number of configurable times per tick". — [Spigot configuration wiki](https://www.spigotmc.org/wiki/spigot-configuration/)
- Sponge `entity-collisions.max-entities-within-aabb` (default 8): "Maximum amount of entities any given entity or block can collide with", per-mod/per-entity overrides, 0 disables. — [Sponge global.conf docs](https://docs.spongepowered.org/stable/en/server/getting-started/configuration/sponge-conf.html)
- Paper guidance: lowering `max-entity-collisions` to 2 reduces work in mob piles, but values below 3 can be game-breaking, and setting 2 prevents the `maxEntityCramming` gamerule from working properly unless set >= the gamerule. — [Paper config optimization guide (dedicatedmc)](https://docs.dedicatedmc.io/server-optimization/paper-config-optimization-guide/amp/)
- Lithium (1.15+ Fabric; Radium is the Forge port): entity collision optimizations; static analysis of Entity classes into "class groups" (entities with hitboxes like boats/shulkers, or special collision behaviour like boats/minecarts) so collision code avoids scanning all entities; "unpushable cramming" keeps a separate list of pushable entities for cramming tests; oversized-block tracking per chunk section to shrink suffocation/collision block scans. — [Lithium NeoForge mixin config](https://github.com/CaffeineMC/lithium/blob/develop/lithium-neoforge-mixin-config.md); [Lithium config wiki](https://github.com/CaffeineMC/lithium/wiki/Configuration-File/338ae7e6b01018aa9cb81f06ddf3c95b64c13a7e)

### Inferences
- The `getCollisionBoxes` entity scan is pure overhead for NPCs in a crowd of other NPCs, because `EntityNPCInterface` (and most living entities) return null from `getCollisionBoundingBox()`; only a few classes (boats, shulkers, some modded entities) contribute boxes. A Lithium-style "skip if no entity class in this region overrides getCollisionBoundingBox" check would be behaviour-neutral if the classification is conservative (any class overriding the method, including modded ones, counts as "has box"). Risk: mods that compute boxes dynamically; must be a switch.
- Another behaviour-neutral idea specific to an owned entity: when the NPC has no hitbox (`getHasHitbox()==false`, so `canBePushed()` false), check whether its `collideWithNearbyEntities` can be skipped — but vanilla still runs cramming damage and `collideWithEntity` on others from the NPC's side, so skipping is only neutral if every effect of that loop is provably absent for that NPC configuration. Needs code-level verification.
- If any installed mod raises `World.MAX_ENTITY_RADIUS` (some large-entity mods do), every NPC's two per-tick queries widen to more chunks; this is worth checking in the server's mod list when profiling (Universal Tweaks' "Entity Radius Check" exists precisely for that).
- Capping collisions (Spigot/Sponge style) changes pushing and cramming — behaviour change, switch default off.

### Gaps
- No published 1.12 measurement of per-tick collision cost vs. entity density was found.
- Which specific 1.12 mods raise `MAX_ENTITY_RADIUS` was not established from a primary source.

## 4. Entity tracking and server networking

### Takeaway
1.12 `EntityTracker.tick()` calls `updatePlayerList(world.playerEntities)` for every tracked entity every tick (O(tracked entities x players)), and each entry sends movement every `updateFrequency` ticks, plus immediately whenever the DataManager is dirty or the entity is airborne, plus a full teleport at least every 400 ticks; CustomNPCs registers NPCs with range 64, frequency 3, velocity updates on. Proven later-version fixes (Paper distance maps, reduced tracker updates) give large gains with many players but change visibility latency; for a mod, the behaviour-neutral levers are avoiding needless metadata dirtying and avoiding redundant custom packets.

### Cited Findings
- `EntityTracker.tick()`: `for (EntityTrackerEntry e : entries) e.updatePlayerList(world.playerEntities);` — [local: dev/build/tmp/recompileMc/sources/net/minecraft/entity/EntityTracker.java lines 291-308]
- `EntityTrackerEntry`: sends updates when `updateCounter % updateFrequency == 0 || isAirBorne || getDataManager().isDirty()`; metadata sent only when DataManager dirty; "every 400 ticks a full teleport packet is sent"; velocity packet when `velocityChanged`. — [local: dev/build/tmp/recompileMc/sources/net/minecraft/entity/EntityTrackerEntry.java lines 100-103, 188-250, 316-331]
- CustomNPCs NPC registration: `registerNewentity(name, 64, 3, true)` -> `EntityEntryBuilder.tracker(range=64, updateFrequency=3, sendsVelocityUpdates=true)`. — [local: dev/reference-src/noppes/npcs/CustomEntities.java lines 68-74]
- Spigot `entity-tracking-range` defaults: players 48, animals 48, monsters 48, misc 32, other 64; described as mainly affecting client-side performance. — [Spigot configuration wiki](https://www.spigotmc.org/wiki/spigot-configuration/)
- Paper PR #2970 "Reduce entity tracker updates on move": tracker updates on player movement batched; measured up to 4x less movement-packet processing time; 100 players TPS ~9.5 -> ~15.5; 110 players 12 -> 16-17. Behaviour change: when players stand still, entity visibility updates take 20-40 ticks; new entities still immediately visible. — [PaperMC PR #2970](https://github.com/PaperMC/Paper/pull/2970)
- Paper distance-map work (Spottedleaf): players indexed by area in pooled hash tables, so "looking up players in a specific location will be approximately constant time", scaling better with players. — [PaperMC PR #2171](https://github.com/PaperMC/Paper/pull/2171); [PaperMC PR #2958](https://github.com/PaperMC/Paper/pull/2958)
- EntityTrackerFixer (Spigot plugin, 1.14+) targets entities "tracked further than they need to be" and claims big TPS effects on 1.14.4-1.16 servers with >30 players (plugin claim, no methodology). — [EntityTrackerFixer on SpigotMC](https://www.spigotmc.org/resources/entitytrackerfixer-fix-1-14-4-1-16-2-entitytick-lag.70902/)
- Universal Tweaks: "Entity Tracker: Fixes entity tracker to prevent client-sided desyncs when teleporting or changing dimensions" (a correctness fix, not a speed fix). — [Universal Tweaks README](https://github.com/ACGaming/UniversalTweaks)
- FoamFix (1.12.2) includes "minor network optimization and config options to change deflater compression strength". — [FoamFix search summary / CurseForge](https://www.curseforge.com/minecraft/mc-mods/foamfix-optimization-mod)
- CustomNPC+ (1.7.10) added "Fully Multithreaded Packet Sending" in 1.8.2 and removed it in 1.8.3 "due to synchronization issues"; 1.10 "Completely remade Packet System". — [CustomNPC+ releases](https://github.com/KAMKEEL/CustomNPC-Plus/releases)

### Inferences
- With hundreds of NPCs and few players, `updatePlayerList` per entity is cheap per call but scales with entries x players; for the target scenario (hundreds of NPCs, small player count) tracker cost is probably secondary to AI/pathfinding/collision, but should be confirmed with a profile.
- Behaviour-neutral levers inside the mod: ensure NPC code does not set DataManager values to equal values in ways that mark them dirty (in 1.12 `EntityDataManager.set` only marks dirty when `ObjectUtils.notEqual(value, current)` [local: dev/build/tmp/recompileMc/sources/net/minecraft/network/datasync/EntityDataManager.java lines 158-163], but `setDirty(key)` at line 170 marks dirty unconditionally, so mutable values such as NBT/ItemStack re-sent via `setDirty` or replaced with new-but-equal objects deserve a check), and avoid sending per-tick custom (non-vanilla) sync packets for unchanged state. Changing tracker range/frequency (64/3) changes what clients see and when — behaviour change, and it touches registration, not packet IDs; still switch-only.
- CNPC+'s reverted multithreaded packet sending is a concrete cautionary example for the forbidden "multithreading" category.

### Gaps
- No 1.12 Forge mod that optimizes `EntityTracker` for speed (as opposed to desync fixes) was found; "Packet Fixer" was not researched (it addresses packet size limits, not tick cost, per general knowledge — unverified).
- No measurement of CustomNPCs' own custom-packet volume per NPC was found.

## 5. Script engines: Nashorn cost, per-NPC engines, CustomNPC+ approach

### Takeaway
Original CustomNPCs creates a new Nashorn `ScriptEngine` per `ScriptContainer` via `factory.getScriptEngine()`, which per Nashorn guidance defeats the engine's compiled-script cache and multiplies memory; the recommended pattern (single engine, separate bindings/global per context, precompiled `CompiledScript`) changes global-scope semantics, so in this project it can only be an opt-in switch. CustomNPC+ (1.7.10) added a Janino-compiled Java scripting option and reports "Improved Script Performance" and "optimized function lookup speeds", without published numbers.

### Cited Findings
- CustomNPCs `ScriptController` registers `NashornScriptEngineFactory` and `getEngineByName(language)` returns `factory.getScriptEngine()` (a new engine every call); `ScriptContainer` calls it to obtain `this.engine`. Optional `nashorn.args` system property from config. — [local: dev/reference-src/noppes/npcs/controllers/ScriptController.java lines 61-81, 259-265; dev/reference-src/noppes/npcs/controllers/ScriptContainer.java line 209]
- Nashorn guidance (nashorn-dev mailing list): share a single ScriptEngine, compile a stateless library once at startup (in the thread, compiling took 500+ ms), evaluate small scripts against it; sharing contexts/bindings across engines does not work reliably; "javascript does not define multithreaded semantics". — [nashorn-dev, Oct 2014](https://mail.openjdk.org/pipermail/nashorn-dev/2014-October/003760.html)
- CometD case: "Every JavaScript instance got its own engine instance", which prevented Nashorn from reusing cached precompiled scripts and exhausted memory; fixed by one shared engine with distinct bindings and nulling references for GC. — [cometd issue #737](https://github.com/cometd/cometd/issues/737)
- `NashornScriptEngine` implements `Compilable` and `Invocable` (precompile once, invoke many). — [NashornScriptEngine javadoc 8u40](https://cr.openjdk.org/~sundar/jdk.nashorn.api/8u40/javadoc/jdk/nashorn/api/scripting/NashornScriptEngine.html)
- Nashorn compiles JS to JVM bytecode using invokedynamic and was 2-10x faster than Rhino. — [Oracle: Nashorn article](https://www.oracle.com/technical-resources/articles/java/jf14-nashorn.html)
- CustomNPC+ supports Java scripting compiled by Janino (classes, generics, lambdas, method references) and Nashorn-based JavaScript (ECMAScript 5.1). — [CustomNPC+ GitHub](https://github.com/KAMKEEL/CustomNPC-Plus)
- CustomNPC+ release notes: 1.8.4 "Improved Script Performance"; 1.10.2 "improved scripting performance with optimized function lookup speeds" (CurseForge file notes); script exceptions reported to a Script Console; `java.lang.reflect` banned in scripts. — [CustomNPC+ releases](https://github.com/KAMKEEL/CustomNPC-Plus/releases); [CustomNPC+ 1.10.2 on CurseForge](https://www.curseforge.com/minecraft/mc-mods/customnpc-plus/files/7074823); [CustomNPC+ npc-and-tools.md](https://github.com/KAMKEEL/CustomNPC-Plus/blob/master/update/npc-and-tools.md)
- A separate "Nashorn (Custom NPCS ECMAScript)" mod exists on CurseForge for 1.7.10, indicating Nashorn availability depends on the Java runtime. — [Nashorn 1.7.10 mod on CurseForge](https://www.curseforge.com/minecraft/mc-mods/nashorn-1-7-10)

### Inferences
- "Function lookup speed" in CNPC+ most likely refers to caching which script hook functions exist (avoiding `invokeFunction` attempts / exceptions for missing hooks every event). A per-container cache of "does function X exist" is behaviour-neutral as long as it is invalidated on script reload and on any runtime redefinition of globals — a good switchable candidate for this project.
- Moving to one shared engine with per-NPC `ScriptContext`/global changes semantics (shared prototypes, `Java.type` caches, global pollution) and engine creation time vs. memory trade-offs; treat as a separate opt-in feature, not a default.
- Per-tick script hooks (`tick` event) on hundreds of NPCs multiply interpreter cost linearly; caching hook existence avoids paying the cost when the hook is absent.
- Nashorn is JDK-8 bound for 1.12.2; it was deprecated in JDK 11 and removed in JDK 15 per general knowledge (JEP 372) — not verified in this session.

### Gaps
- No published measurement of per-engine memory/CPU cost in CustomNPCs found.
- No evidence of global locks in CustomNPCs scripting was found in web sources; local code was not checked for `synchronized` in script paths.
- CNPC+ commit-level details of "optimized function lookup" were not retrieved.

## 7. Profiling tools usable on 1.12.2 servers

### Takeaway
spark is usable on 1.12.2 Forge (official 1.4.3/1.5.2/1.6.3 builds, or the Mixin-based "Spark Unforged" backport with newer features); on Windows spark cannot use async-profiler and falls back to the safepoint-biased Java sampler (WarmRoast-based). JFR is available in OpenJDK 8u262+ (compiled in by default from 8u272). LagGoggles gives per-entity microseconds/tick (needs TickCentral). The vanilla profiler already exposes `goalSetup`, `goalTick` and `pathfind` sections.

### Cited Findings
- spark official Forge 1.12.2 builds exist on CurseForge (e.g. 1.4.3, 1.5.2, 1.6.3). — [spark 1.6.3 (Forge 1.12.2)](https://www.curseforge.com/minecraft/mc-mods/spark/files/3542217); [spark 1.4.3 (Forge 1.12.2)](https://www.curseforge.com/minecraft/mc-mods/spark/files/3164181); [spark 1.5.2](https://www.curseforge.com/minecraft/mc-mods/spark/files/3245793)

## 8. Forbidden-by-project techniques (documented for trade-off awareness)

### Takeaway
The most popular server optimizations for crowds of mobs — activation range (Spigot/Sponge), Pufferfish DAB, Tick Dynamic/Tiquality time-slicing, collision caps, nerfed spawner mobs, and multithreaded entity work (Performant, Async, CNPC+'s reverted packet threading) — all buy TPS by changing when or whether entities run, with documented behavioural side effects and in some cases bugs.

### Cited Findings
- Spigot entity-activation-range (defaults animals 32, monsters 32, misc 16): entities outside range tick at a reduced rate; "Lowering these values can give a major boost to performance, but at the cost of affecting gameplay behavior"; `tick-inactive-villagers=false` makes villagers not work as in vanilla. — [Spigot configuration wiki](https://www.spigotmc.org/wiki/spigot-configuration/)
- Activation range immunity: new/baby mobs, mobs in water (non-water mobs), mobs aggressive to a player, burning mobs; inactive entities still get an `inactiveTick`. — [Paper spigot.yml reference](https://docs.papermc.io/paper/reference/spigot-configuration/); [SPIGOT-3894](https://hub.spigotmc.org/jira/si/jira.issueviews:issue-html/SPIGOT-3894/SPIGOT-3894.html)
- Paper issue #5083: a logic error in "Entity Activation Range 2.0" made inactive entities' pathfinders tick every tick (fixed by PR #5085) — example of how throttling code silently goes wrong. — [PaperMC issue #5083](https://github.com/PaperMC/Paper/issues/5083)
- SpongeForge 1.12.2 entity-activation-range module: per-type defaults ambient/aquatic/creature/monster 32, misc 16, per-mod overrides, `auto-populate`. — [Sponge global.conf docs](https://docs.spongepowered.org/stable/en/server/getting-started/configuration/sponge-conf.html); [Sponge performance tweaks](https://docs.spongepowered.org/stable/en/server/management/performance-tweaks.html)
- Pufferfish DAB: tick frequency on a distance gradient, `freq = distanceToPlayer^2 / 2^activation-dist-mod` (default 8, "never below 6"); lowering affects how entities interact and may break farms. Issue: "DAB drowns AI entities far away from the player". — [Pufferfish fork configuration](https://docs.pufferfish.host/setup/pufferfish-fork-configuration/); [YouHaveTrouble optimization guide](https://github.com/YouHaveTrouble/minecraft-optimization/blob/1.21/README.md); [Pufferfish issue #58](https://github.com/pufferfish-gg/Pufferfish/issues/58)
- Tick Dynamic (1.8.9-1.12.2 Forge coremod): divides the 50 ms tick into time slices per world and per entity/TE group, throttling individual updates under load, with `minimumObjects` to prevent starvation; not SpongeForge compatible; can cause stutter. — [Tick Dynamic on CurseForge](https://www.curseforge.com/minecraft/mc-mods/tick-dynamic)
- Tiquality (1.12): "Limiting a player's tick time in the world to evenly distribute time". — [UsefulMods 1.12 performance list](https://github.com/TheUsefulLists/UsefulMods/blob/main/Performance/Performance112.md)
- Spigot `nerf-spawner-mobs`: spawner mobs "will not have any AI". — [Spigot configuration wiki](https://www.spigotmc.org/wiki/spigot-configuration/)
- Multithreading: Performant (1.14-1.16.5) multithreads collisions and pathing; the Async mod (1.21.1) has an issue where non-player entities clip through blocks and suffocate after an upgrade; CNPC+ removed multithreaded packet sending "due to synchronization issues". — [Performant](https://www.curseforge.com/minecraft/mc-mods/performant); [AxalotLDev/Async issue #109](https://github.com/AxalotLDev/Async/issues/109); [CustomNPC+ releases](https://github.com/KAMKEEL/CustomNPC-Plus/releases)
- Collision caps (Spigot/Paper/Sponge, see section 3) are behaviour changes (pushing/cramming).

### Inferences
- All of these are incompatible with constraint F (or at minimum with "original as default"); they are popular because they scale cost with players' proximity rather than with entity count, which is the only way to get order-of-magnitude gains without rewriting algorithms. Their side effects (frozen far NPCs, delayed reactions, broken schedules/jobs, drowning, farm breakage, race conditions) are exactly the kinds of behavioural drift the project wants to avoid.
- If a future separate project revisits this, the Spigot "immunity" list is a useful model: NPCs in combat, with active scripts, with jobs/roles that must run, or recently spawned should be exempt.

### Gaps
- No published before/after MSPT numbers for activation range or DAB on a CustomNPCs server were found.
- Lighting mods (Phosphor/Hesperus/Alfheim) and FoamFix were confirmed to exist for 1.12.2 ([UsefulMods list](https://github.com/TheUsefulLists/UsefulMods/blob/main/Performance/Performance112.md); [Hesperus](https://www.curseforge.com/minecraft/mc-mods/hesperus)) but are not NPC-AI optimizations; their relevance to NPC tick cost was not assessed. BetterFps and Fastcraft were not researched (BetterFps is primarily client-side; Fastcraft is 1.7.10-era and closed-source — general knowledge, unverified).
