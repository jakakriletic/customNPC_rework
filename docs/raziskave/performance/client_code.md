## Q1. How is one NPC rendered per frame (model path, display lists, part count, rebuilds, allocations, GL state, texture binds)?

### Takeaway
The default humanoid `EntityCustomNpc` is NOT immediate-mode: every body part is a display list compiled once per renderer (shared by all NPCs of that entity class) and never rebuilt, so per-NPC cost is a fixed ~18 `glCallList`s plus matrix work, ~7 layer push/pop wrappers, one per-NPC immediate Tessellator draw for the eyes, the vanilla shadow, and optional second full-model pass for overlay textures; the real multipliers are optional features (armor + enchant glint, held items, chat bubbles, name tags, particle parts, "morph" entity models) rather than the base model.

### Cited Findings
- Renderer registration: `EntityCustomNpc` → `new RenderCustomNpc(new ModelPlayerAlt(0.0f,false))` (one renderer + one model instance for the whole class); Alex/64x32/Classic variants each get their own instance — [RS/client/ClientProxy.java:262-266](dev/reference-src/noppes/npcs/client/ClientProxy.java)
- `ModelScaleRenderer.render()` compiles its cube list into a display list on first use (`isCompiled` flag, `GLAllocation.generateDisplayLists(1)` + `glNewList(...,GL_COMPILE)`), then every frame only does push → `postRender` (translate by part config, vanilla rotate, scale by part config) → `callList` → children → pop. There is no code path that resets `isCompiled`, i.e. lists are never rebuilt on model-data change — [RS/client/model/ModelScaleRenderer.java:50-66, 68-76, 87-96](dev/reference-src/noppes/npcs/client/model/ModelScaleRenderer.java)
- Per-NPC body proportions are applied as GL `translate/scale` from `ModelPartConfig` at render time (not baked into the list), which is why sharing one compiled list across all NPCs works — [RS/client/model/ModelScaleRenderer.java:68-76](dev/reference-src/noppes/npcs/client/model/ModelScaleRenderer.java); per-frame binding of configs in `setRotationAngles` loop over `map.keySet()` — [RS/client/model/ModelPlayerAlt.java:102-111](dev/reference-src/noppes/npcs/client/model/ModelPlayerAlt.java)

### Inferences
- Draw-call budget for a "bare" default NPC (skin type 0, no parts, no armor, no item, eyes on, HeadWearType 1): 11 body callLists + 7 headwear callLists = **~18 display-list calls**, plus 1 immediate Tessellator draw (eyes), 1 shadow draw, and ~25–40 matrix push/pop/translate/rotate/scale ops, ~7 layer wrappers. A name tag adds 1–3 font strings (Q2). At 300 visible NPCs that is ≈5,400 callLists + ≈600 small immediate draws per frame from NPC bodies alone: a CPU/driver-bound workload (display-list call overhead + fixed-function matrix ops), not a vertex-bound one.
- Feature multipliers (per NPC, rough): overlay texture ×2 body cost; each armor piece +1–2 binds, +~6 callLists, +glint pass if enchanted; each held item = immediate-mode item quads every frame; each part +1 bind +1–10 callLists; morph models = whatever the vanilla/mod model costs plus its layers.
- Because display lists are shared per renderer and never rebuilt, "model caching" in the sense of avoiding rebuilds is already solved; the remaining wins are batching/state reduction (e.g. skip empty layer wrappers, merge eyes into a display list or the head pass, skip `setupFogColor`) and LOD (skip layers/parts/eyes beyond N blocks).
- Allocation pressure per NPC per frame is small (a few iterators) except chat-bubble NPCs; GC is unlikely to be the main client cost from the body path. The [ENT] `Pose` maps are a heavier per-frame allocation source when that mod is combined (several HashMaps per animated NPC per frame).
- The 2-pass overlay and the empty-if ray trace are cheap fixes that keep visuals identical.

### Gaps
- No client profiling exists; the relative weight of display-list calls vs. matrix ops vs. state changes vs. driver cost on the user's GPU is unknown (OptiFine, if used, changes the entity path and was not examined).
- Exact quad/vertex counts per part were not tallied; texture size of `moreplayermodels` part PNGs not checked.
- `NPCRendererHelper` (in `net.minecraft.client.renderer.entity` package of the mod) was not read in full.

## Q2. Name tags, titles, health bars, speech/chat bubbles: how rendered, distance, culling?

### Takeaway
Names are forced on for every NPC (`getAlwaysRenderNameTagForRender() == true`) and drawn with vanilla `FontRenderer` (per-character immediate-mode GL) within √512 ≈ 22.6 blocks, twice when the player is within 4 blocks; chat bubbles use 18 separate immediate Tessellator draws plus a font pass, drawn twice within 4 blocks, and allocate a fresh `TreeMap` every frame forever once an NPC has spoken. There is no CNPC health bar over heads (only the vanilla boss bar).

### Cited Findings
- NPC always requests its name tag: `getAlwaysRenderNameTagForRender() { return true; }` — [PS/entity/EntityNPCInterface.java:1051-1053](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java); vanilla `canRenderName` then requires GUI enabled, not invisible, not ridden, team visibility — [MC] `net/minecraft/client/renderer/entity/RenderLivingBase.java:480-511`
- CNPC overrides `renderName`: returns if `getDistanceSq(viewer) > 512` (≈22.6 blocks; vanilla uses `NAME_TAG_RANGE = 64` blocks [MC] `RenderLivingBase.java:35, 462-474`); renders chat bubbles first, then the label if `display.showName()` — [RS/client/renderer/RenderNPCInterface.java:57-74](dev/reference-src/noppes/npcs/client/renderer/RenderNPCInterface.java); `showName()` = mode 0 always, mode 2 only while attacking — [RS/entity/data/DataDisplay.java:148-153](dev/reference-src/noppes/npcs/entity/data/DataDisplay.java)
- `renderLivingLabel`: per label ~15 GL state/matrix ops, title drawn once with string concat, name drawn **twice when within 4 blocks** (once with depth test disabled as see-through, once normal), once otherwise; `npc.getFaction().color` looked up per frame — [RS/client/renderer/RenderNPCInterface.java:84-122](dev/reference-src/noppes/npcs/client/renderer/RenderNPCInterface.java)
- Vanilla 1.12 `FontRenderer` draws each default-font character with `glBegin(GL_TRIANGLE_STRIP)` … `glEnd` (immediate mode per glyph) — [MC] `net/minecraft/client/gui/FontRenderer.java:~205-220`
- Chat bubbles (`EnableChatBubbles = true` default [RS/CustomNpcs.java:121](dev/reference-src/noppes/npcs/CustomNpcs.java)): `RenderChatMessages` object is created lazily on the first CHATBUBBLE packet for that NPC and never removed — [RS/client/PacketHandlerClient.java:106-119](dev/reference-src/noppes/npcs/client/PacketHandlerClient.java)
- `renderMessages` calls `getMessages()` which **allocates a new `TreeMap` every frame** and copies non-expired (10 s) entries, even when all are expired — [RS/client/RenderChatMessages.java:61-70, 166-175](dev/reference-src/noppes/npcs/client/RenderChatMessages.java)
- When a bubble is active: rendered twice within 4 blocks (no-depth + depth passes); each pass draws **18 rectangles, each with its own `Tessellator.begin/draw`**, then each text line via `FontRenderer` — [RS/client/RenderChatMessages.java:67-69, 72-138, 140-164](dev/reference-src/noppes/npcs/client/RenderChatMessages.java). `addMessage` copies the TreeMap and constructs `TextBlockClient` (text wrapping) per message — [RS/client/RenderChatMessages.java:42-58](dev/reference-src/noppes/npcs/client/RenderChatMessages.java)
- Boss bar: only vanilla `BossInfoServer` updates (`bossInfo.setPercent` each living update) — [PS/entity/EntityNPCInterface.java:481-483, 521-523](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java); no per-NPC overhead health-bar renderer was found under `RS/client/renderer`.

### Inferences
- Labels are culled only by distance (22.6 blocks) and by the entity frustum check (the label is drawn from `Render.doRender`, which only runs for entities that passed `shouldRender`). There is no occlusion test, no label budget, no "fade at distance". In a crowd of 300 NPCs within ~22 blocks, a 12-character name+title costs ~25–40 immediate-mode glyph primitives per NPC → several thousand `glBegin/glEnd` per frame; within 4 blocks the name is doubled.
- The per-frame `TreeMap` per "has ever spoken" NPC is a pure waste after the 10 s expiry (allocation + iteration every frame); an early exit when the map is empty or a cached expiry timestamp would remove it without visual change.
- Low-risk switches (default = original): label distance limit (keep 512 by default), skip the doubled see-through pass beyond N NPCs, cache glyph strings into display lists per NPC name (invalidate on name/title/faction-color change), bubble rects batched into one draw.

### Gaps
- Visual equivalence of a display-list-cached name tag vs. FontRenderer (e.g. Unicode font, formatting codes, OptiFine custom fonts) was not verified.
- `TextBlockClient` wrapping cost was not measured.

## Q3. Skins: URL download threads, caching, texture memory, re-uploads

### Takeaway
URL skins (skinType 2) are deduplicated per URL in the `TextureManager` (key = `skins/<md5(url)>`), downloaded by one unbounded, timeout-less raw `Thread` per unique URL with no disk cache (cacheFile is `null`), kept forever (never deleted until resource reload / restart) and uploaded at whatever size the server returns; player-profile skins (skinType 1) can re-query the vanilla skin cache every frame until resolved. The plan does mention the skin download issue (executor, timeouts, dedup) but not memory/size limits.

### Cited Findings
- `getEntityTexture`: skinType 0 → cached `ResourceLocation`; skinType 1 → `SkinManager.loadSkinFromCache(profile)` each call until a SKIN entry is found (the result is cached only on success); skinType 2 → MD5 of URL → `ResourceLocation("skins/"+hex)` → `loadSkin` — [RS/client/renderer/RenderNPCInterface.java:227-262](dev/reference-src/noppes/npcs/client/renderer/RenderNPCInterface.java). For the first 5 client ticks after start all non-file skins return the default — [RS/client/renderer/RenderNPCInterface.java:232-234](dev/reference-src/noppes/npcs/client/renderer/RenderNPCInterface.java), counter incremented in [RS/client/ClientTickHandler.java:64](dev/reference-src/noppes/npcs/client/ClientTickHandler.java)
- `loadSkin` returns early if the TextureManager already has that location (dedup per URL), else registers `new ImageDownloadAlt(null /*cacheFile*/, url, default, new ImageBufferDownloadAlt())` — [RS/client/renderer/RenderNPCInterface.java:264-271](dev/reference-src/noppes/npcs/client/renderer/RenderNPCInterface.java)
- `ImageDownloadAlt.loadTextureFromServer` starts a new daemon `Thread("Texture Downloader #n")` per texture; `HttpURLConnection` without connect/read timeouts; no thread pool or concurrency limit; on non-2xx it silently returns (texture stays default, no retry) — [RS/client/ImageDownloadAlt.java:103-144](dev/reference-src/noppes/npcs/client/ImageDownloadAlt.java). With `cacheFile == null` the disk-cache branch is never used, so every client session re-downloads every URL skin — [RS/client/ImageDownloadAlt.java:80-101](dev/reference-src/noppes/npcs/client/ImageDownloadAlt.java)
- GL upload happens lazily on the render thread in `getGlTextureId()` → `TextureUtil.uploadTextureImage(id, bufferedImage)` once (`textureUploaded` flag); the `BufferedImage` field is never cleared after upload (CPU copy retained) — [RS/client/ImageDownloadAlt.java:47, 58-71](dev/reference-src/noppes/npcs/client/ImageDownloadAlt.java). `ImageBufferDownloadAlt.parseUserSkin` copies the image into a new ARGB `BufferedImage` of the source's full width×height (no size clamp) — [RS/client/renderer/ImageBufferDownloadAlt.java](dev/reference-src/noppes/npcs/client/renderer/ImageBufferDownloadAlt.java) (`parseUserSkin`)
- No code in the client calls `TextureManager.deleteTexture` for NPC skins (grep for skin texture removal found none in `RS/client`); `textureLocation` is reset only when skin type/texture/URL/player changes — [RS/entity/data/DataDisplay.java:129-131, 240-241](dev/reference-src/noppes/npcs/entity/data/DataDisplay.java)
- Part/cape/overlay textures are file resources loaded lazily via `ClientProxy.bindTexture` → `new SimpleTexture(location)` on first use — [RS/client/ClientProxy.java:538-556](dev/reference-src/noppes/npcs/client/ClientProxy.java)
- Plan row "Prenos skinov": "`ImageDownloadAlt` creates a thread for the download; no connect/read timeout … Bounded executor, timeouts, dedup of identical requests, fallback on error" — [PLAN_IMPLEMENTACIJE.md:127](PLAN_IMPLEMENTACIJE.md); test list includes "skin download failure, resource reload, many different skins" — [PLAN_IMPLEMENTACIJE.md:141](PLAN_IMPLEMENTACIJE.md)

### Inferences
- Texture memory per unique 64×64 skin is ~16 KiB GPU (RGBA8, no mipmaps) + ~16 KiB retained heap `BufferedImage`; trivial for hundreds of standard skins. The risk is an oversized URL image (e.g. 2048×2048 ≈ 16 MiB GPU + 16 MiB heap each), which nothing prevents.
- Hundreds of NPCs with distinct URLs entering view at once spawn hundreds of concurrent threads/HTTP connections; a dead host without timeouts pins threads indefinitely (daemon, so no shutdown hang, but resource/socket leak). Frame hitch risk: the GL uploads for many skins can land in the same frame (each upload is on the render thread inside `bindTexture`).
- Dedup is already per-URL, so the plan's "dedup of identical requests" is largely present; what is missing is a disk cache, a size clamp, a bounded executor/timeouts (planned), and optionally releasing the CPU `BufferedImage` after upload.
- skinType 1 NPCs whose profile has no textures keep calling `loadSkinFromCache` (Guava cache lookup keyed by `GameProfile`) every frame — cheap per call but unbounded in count; caching a "not available, retry at tick T" marker would be a safe fix.

### Gaps
- Vanilla `SkinManager.loadSkinFromCache` internals were not re-read; whether a miss can trigger a synchronous session-service call was not verified.
- No data on how many distinct URL skins real servers of the user use.

## Q4. Client tick per NPC: what runs on the client each tick, and its cost

### Takeaway
Client-side CNPC logic per tick is light (no client AI or pathing; script hook returns early on the client); the dominant per-tick client cost is vanilla `EntityLivingBase.onLivingUpdate` (interpolation + `collideWithNearbyEntities` AABB query), with two CNPC exceptions that scale badly: the PARTICLES model part (2 custom particles per NPC per tick, no distance check, each particle breaks particle batching) and "morph" NPCs (a second full entity ticked per NPC).

### Cited Findings
- `EntityNPCInterface.onUpdate` (runs on both sides): every 10 ticks `calculateStartYPos` + `EventHooks.onNPCTick`; every tick `timers.update()`, a dead-state check — [PS/entity/EntityNPCInterface.java:376-394](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java). `onNPCTick` returns immediately when `npc.script.isClient()` (= `world.isRemote`) — [RS/EventHooks.java:142-149](dev/reference-src/noppes/npcs/EventHooks.java), [RS/entity/data/DataScript.java:76-78](dev/reference-src/noppes/npcs/entity/data/DataScript.java). `calculateStartYPos` loops down from the start pos but returns on the first block whose bounding box is non-null — [PS/entity/EntityNPCInterface.java:1401-1416](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java)
- `onLivingUpdate` on the client: `updateArmSwingProgress`, faction lookup every 20 ticks, skips the whole server block (`!world.isRemote`), then vanilla `super.onLivingUpdate()`, then client block: `roleInterface.clientUpdate()` (non-empty only for companions), `cloakUpdate()` if a cape is set, animation change check (`dataManager.get(Animation)` → `updateHitbox()` on change), Bard job music logic — [PS/entity/EntityNPCInterface.java:432-524](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java); `RoleInterface.clientUpdate` is empty by default — [RS/roles/RoleInterface.java:59-60](dev/reference-src/noppes/npcs/roles/RoleInterface.java)
- Bard NPCs on the client do a `getEntitiesWithinAABB(EntityPlayer, …)` every tick while their song is not playing — [RS/roles/JobBard.java:56-81](dev/reference-src/noppes/npcs/roles/JobBard.java)
- Vanilla client part: AI only runs when `isServerWorld()`; client does position interpolation, `travel()` (its movement body is gated by `isServerWorld() || canPassengerSteer()`), and **`collideWithNearbyEntities()` → `getEntitiesInAABBexcluding` every tick** — [MC] `net/minecraft/entity/EntityLivingBase.java:1839, 2306-2396, 2437-2439`

Vanilla caps each particle layer at 16384 — [MC] `net/minecraft/client/particle/ParticleManager.java:191`

### Inferences
- PARTICLES part: steady state ≈ 2 × ~45 ≈ **90 live particles per such NPC**, each costing 2 extra draw calls and 2 texture binds per frame because of the batch break → ~180 draws/NPC/frame. 50 NPCs with a particle part ≈ 4,500 particles ≈ 9,000 draw calls per frame, independent of whether the player can see them (no distance check). This is likely the single largest per-NPC client cost when that part is used; fixable without visual change inside view distance (distance gate as switch; batching per texture would change draw order but not look).
- Morph NPCs roughly double client tick cost per NPC and add the morph entity's full render cost.
- A large `World.MAX_ENTITY_RADIUS` (one very wide NPC) widens every entity AABB query's chunk scan on that side (client and server) — a global side-effect worth noting.
- Base client tick per normal NPC is dominated by vanilla; packed crowds make `collideWithNearbyEntities` O(n·k). This is the same as vanilla mobs and only changeable by altering push behaviour (behaviour change → out of scope by project rules).

### Gaps
- `DataTimers.update()` (patched in `PS/entity/data/DataTimers.java`) client-side cost not read in detail (planned early-exit in M5.4 applies to both sides).
- `NoppesUtil.spawnParticle` (PARTICLE packet handler) not read.

## Q5. Render distance, frustum culling, occlusion

### Takeaway
CNPC does not override `shouldRender`, `isInRangeToRenderDist`, `getRenderBoundingBox`, `ignoreFrustumCheck` or `shouldRenderInPass` for NPCs, so NPCs get vanilla distance + frustum culling and no occlusion culling; effective visibility is bounded by the server tracking range of 64 blocks.

### Cited Findings
- Grep over `RS/entity` and `RS/client/renderer` finds only `EntityProjectile.isInRangeToRenderDist` overridden — [RS/entity/EntityProjectile.java:151](dev/reference-src/noppes/npcs/entity/EntityProjectile.java); none of the render-culling hooks are overridden in the patched `EntityNPCInterface` either — [PS/entity/EntityNPCInterface.java](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java) (grep).
- Vanilla `RenderGlobal.renderEntities` calls `renderManager.shouldRender(entity, camera, …)` (distance + frustum) for each loaded entity — [MC] `net/minecraft/client/renderer/RenderGlobal.java:554, 619`; `Render.shouldRender` = `isInRangeToRender3d(cam) && (ignoreFrustumCheck || camera.isBoundingBoxInFrustum(renderBB.grow(0.5)))` — [MC] `net/minecraft/client/renderer/entity/Render.java:47-56`
- Distance rule: visible if `dist < avgEdge(AABB) × 64 × renderDistanceWeight` — [MC] `net/minecraft/entity/Entity.java:1608-1628`; `renderDistanceWeight = clamp(renderDistanceChunks/8, 1.0, 2.5)` — [MC] `net/minecraft/client/renderer/RenderGlobal.java:867`
- NPC entity tracker registration: range 64, update frequency 3, velocity updates on — [RS/CustomEntities.java:64-69, 71-75](dev/reference-src/noppes/npcs/CustomEntities.java)
- Hitbox/AABB scales with `display.getSize()` (size 5 = normal) — [PS/entity/EntityNPCInterface.java:1129-1149](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java)

### Inferences
- Default NPC AABB (0.6×1.9×0.6) → avg edge ≈1.03 → visible to ≈66 blocks at ≤8 chunks render distance (and more at higher settings), but the server only sends NPCs within 64 blocks, so practical render radius ≈64 blocks: up to ~12,900 m² of ground can hold rendered NPCs. Everything inside the camera frustum in that disc is fully rendered at full detail (no LOD, no occlusion — NPCs behind walls/hills are drawn).
- Candidate safe levers (switch, default off): a per-NPC render distance cap / LOD tiers (e.g. beyond 32 blocks skip eyes, parts, armor glint, held items, layers; beyond 48 blocks body-only), a visible-NPC budget sorted by distance, and an optional cheap occlusion test. All change visuals at distance, so they must be off by default per project rules.

### Gaps
- Whether the user's client uses OptiFine/Entity Culling-type mods (which add occlusion culling) is unknown.

## Q6. Network sync on the client: which packets per NPC, how often, how expensive to handle

### Takeaway
Per NPC the client receives vanilla tracker traffic (relative move/look every 3 ticks while moving, head look, velocity, teleport every ~60 ticks, metadata when dirty), a GZIP-compressed full-NBT spawn payload on every tracking start, a GZIP full-NBT `UPDATE_NPC` whenever server code sets `updateClient`, and a frequent tiny `EYE_BLINK` custom packet (default-on eyes) sent to every player within a 160-block box; CNPC custom packets are handled via `addScheduledTask` on the main thread, and full-NBT handling re-parses model data but does not rebuild display lists.

### Cited Findings
- Tracker: `updateFrequency = 3` → movement/rotation packets on ticks where `updateCounter % 3 == 0` (or when airborne / metadata dirty); forced teleport every 60 ticks or on large move; velocity packets when motion changes; head-look packets on yaw change; metadata sent when `dataManager.isDirty()` — [RS/CustomEntities.java:68](dev/reference-src/noppes/npcs/CustomEntities.java), [MC] `net/minecraft/entity/EntityTrackerEntry.java:179, 212, 217-240, 264, 295, 311-317`
- NPC metadata keys: Attacking, Animation, RoleData (String), JobData (String), FactionData, Walking, Interacting, IsDead — [PS/entity/EntityNPCInterface.java:231-238, 362-369](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java); server sets `Walking` and `Interacting` every tick (dirty only on change) — [PS/entity/EntityNPCInterface.java:484-485](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java)
- Spawn: `EntityNPCInterface implements IEntityAdditionalSpawnData`; `writeSpawnData` builds an NBT with display, MaxHealth, armor and weapons item maps, AI fields, role/job (+Bard/Puppet/Companion sub-tags) and full `ModelData`, serialized via `Server.writeNBT` = **GZIP** — [PS/entity/EntityNPCInterface.java:227, 1520-1565](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java), [RS/Server.java:265-273](dev/reference-src/noppes/npcs/Server.java). Client `readSpawnData` → `Server.readNBT` (GZIP inflate, `NBTSizeTracker.INFINITE`) → sets fields, rebuilds item maps, `modelData.readFromNBT` (allocates a new parts `HashMap`), `display.readToNBT` — [PS/entity/EntityNPCInterface.java:1567-1607](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java), [RS/Server.java:278-285](dev/reference-src/noppes/npcs/Server.java), [RS/ModelDataShared.java:62-82](dev/reference-src/noppes/npcs/ModelDataShared.java)
- `UPDATE_NPC`: server `updateClient()` sends the same full spawn NBT + EntityId via `sendAssociatedData` — [PS/entity/EntityNPCInterface.java:526-531](dev/src/patch/java/noppes/npcs/entity/EntityNPCInterface.java); client parses it and calls `readSpawnData(compound)` — [RS/client/PacketHandlerClient.java:215-221](dev/reference-src/noppes/npcs/client/PacketHandlerClient.java). `updateClient = true` is set from 65 places, incl. every `DataDisplay` setter (name, title, texture, size, …) and `NPCWrapper` script API setters — e.g. [RS/entity/data/DataDisplay.java:167-273](dev/reference-src/noppes/npcs/entity/data/DataDisplay.java), [RS/api/wrapper/NPCWrapper.java:58, 151, 229](dev/reference-src/noppes/npcs/api/wrapper/NPCWrapper.java). After `readToNBT`, glow and cloak `ResourceLocation`s are always reset, skin location only if skin changed — [RS/entity/data/DataDisplay.java:129-133](dev/reference-src/noppes/npcs/entity/data/DataDisplay.java)
- `sendAssociatedData` targets all `EntityPlayerMP` within an AABB grown by **160 blocks** (not the 64-block tracking set), builds the buffer on `CustomNPCsScheduler` and sends a copy per player — [RS/Server.java:93-116](dev/reference-src/noppes/npcs/Server.java)
- `EYE_BLINK`: each alive NPC with eyes enabled (default) has a 1/140 chance per server tick to blink when idle, then waits 300 ms + 20 ticks — [RS/ModelEyeData.java:61-78](dev/reference-src/noppes/npcs/ModelEyeData.java); client handler sets `blinkStart = currentTimeMillis()` — [RS/client/PacketHandlerClient.java:127-133](dev/reference-src/noppes/npcs/client/PacketHandlerClient.java)
- Every CNPC custom packet is queued with `Minecraft.addScheduledTask` (lambda + task object), decoded by enum ordinal, and logged via `LogWriter.debug` string concat — [RS/client/PacketHandlerClient.java:95-102, 323-337](dev/reference-src/noppes/npcs/client/PacketHandlerClient.java)
- `CHATBUBBLE` packets run `NoppesStringUtils.formatText` and `addMessage` (TreeMap copy + text wrap) — [RS/client/PacketHandlerClient.java:106-119](dev/reference-src/noppes/npcs/client/PacketHandlerClient.java)

### Inferences
- EYE_BLINK rate ≈ 1 per ~166 ticks per NPC (≈0.12/s); 300 NPCs within 160 blocks ≈ 36 custom packets/s per player, each a separate `FMLProxyPacket` + scheduled task on the client. Small per packet, but it is pure cosmetic traffic that ignores tracking range (players 64–160 blocks away receive blinks for NPCs they don't even have). It is also a server-side `getEntitiesWithinAABB(160)` per blink.
- Spawn burst: entering a town with 300 NPCs = 300 GZIP inflates + NBT parses + item-map builds on the client main thread within a few ticks (vanilla processes spawn packets on the main thread) → hitch risk. Size per NPC depends on ModelData/inventory (not measured).
- `UPDATE_NPC` is full-state; scripts that touch display setters every tick (e.g. changing name/title as a status display) would generate a full GZIP NBT per tick per NPC to every player within 160 blocks, plus a client re-parse. No display-list rebuild occurs (lists are shared), so the client cost is parse + small allocations.
- Packet IDs/NBT must stay unchanged (project rule), so safe options are server-side throttling/coalescing of `updateClient` (at most once per tick already, since it's a flag) and limiting `sendAssociatedData` recipients to the tracking set behind a switch (behaviour-identical for players who can see the NPC).

### Gaps
- No byte-size measurement of spawn/UPDATE_NPC payloads; no count of `updateClient` triggers in real scripts.
- `SyncController` login sync (factions, quests, dialogs) client-side parse cost was not examined.

2. **C1 – PARTICLES part: distance gate + batch-safe rendering** (high gain where used, low risk): add the 16-block check the generic overload already has; avoid the per-particle `draw()`/rebind (`EntityEnderFX.java:55-89`). Visual identical within the gate.
3. **C2 – Zero-visual-change micro fixes** (low–medium gain, very low risk): early-out in `RenderChatMessages.getMessages` when empty/expired (no per-frame TreeMap); remove/guard the discarded `canSee` ray trace (`RenderNPCInterface.java:162-164`); cache `"<title>"`; skip empty `LayerInterface` wrappers when the NPC has no part for that layer; replace `keySet()` iteration with a fixed array in `ModelPlayerAlt/ModelBipedAlt.setRotationAngles`; cache faction color per tick.

6. **C5 – Client LOD / render budget** (largest potential gain at 300+ visible NPCs, visual change ⇒ default off): distance tiers that skip eyes, parts, held items, armor glint, overlay pass, labels; optional max-rendered-NPCs budget by distance. 7. **C6 – Skin pipeline hardening** (stability/hitch gain, low risk; partly planned): bounded executor + timeouts (planned row), disk cache (pass a real `cacheFile`), max image size clamp, release `BufferedImage` after upload, spread GL uploads (≤N per frame), retry/backoff marker for skinType 1 misses; texture-memory metric in C0.
8. **C7 – Network cosmetics** (low–medium gain, low risk): restrict `sendAssociatedData` for EYE_BLINK/UPDATE_NPC to the entity's tracking players (switch); optionally drive blinks client-side (visual-only randomness; changes timing ⇒ off by default); measure spawn payload sizes and the GZIP burst on entering crowded areas.
9. **C8 – Morph NPC cost** (niche, medium risk): skip ticking the morph entity when far/not rendered; requires checking mods whose renderers depend on ticking state.
10. **C9 – Combined-mod check with [ENT]** (medium, low risk): pool/reuse `Pose` maps in `AnimatedModel.buildPose`; move `ModelIceGolem` to display lists; include animated NPCs in C0 scenarios.
